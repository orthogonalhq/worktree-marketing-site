## Card 02: Secure Cell architecture

### Card copy

**Label:** Secure Cell architecture

**Heading:** Keep sensitive data scoped to one authorized execution.

### Card visual copy

- Identity verified
- Single authorized execution

### Expansion introduction

**Label:** Secure cell architecture

**Heading:** Sensitive data is decrypted for one authorized agent execution.

**Body:** Each client and practitioner operates inside an isolated cell. When an agent needs sensitive information, a biometric check opens one authorized session. Only the requested data is decrypted inside that cell, and the working context is destroyed after the response is produced.

**Link:** Developer documentation — Upcoming

### Architectural invariant

Sensitive data is unavailable to the agent until a person authorizes a specific request inside the correct cell.

- **Default state:** Encrypted and unavailable
- **Authorization:** One request, one session
- **Execution scope:** One isolated client cell

### Execution lifecycle

**Heading:** What happens when an agent requests a sensitive record.

#### 01. Request

The agent asks for a specific piece of sensitive data.

The record remains encrypted. Nothing sensitive has entered the agent's working context.

- **Data state:** Encrypted
- **Agent access:** None

#### 02. Boundary selection

The request is routed to the client and practitioner's isolated cell.

The execution boundary is established before any protected information is released.

- **Data state:** Encrypted
- **Agent access:** None

#### 03. Biometric authorization

An authorized person approves this request.

The biometric check creates one session for this request. It does not grant the agent ongoing access.

- **Session:** Authorized
- **Scope:** Single execution

#### 04. Execution inside the cell

Only the requested data is decrypted inside the isolated boundary.

The agent can use that context to produce one response without gaining access to another client's data.

- **Data state:** Decrypted in cell
- **Agent access:** This execution

#### 05. Response and teardown

The result is returned, the session closes, and the working context is destroyed.

A later request begins from the closed state and requires a new authorization.

- **Session:** Closed
- **Working context:** Destroyed

### Data state

**Heading:** Before, during, and after the execution.

- **Before authorization — Closed:** Sensitive records remain encrypted. The agent has no sensitive client context.
- **During execution — Open once:** The requested data is decrypted inside the selected cell for the authorized execution.
- **After response — Closed again:** The authorization ends and the decrypted working context is destroyed.

### What the boundary accomplishes

**Heading:** Isolation is the control, not a promise that the model is infallible.

- One client's execution does not inherit another client's decrypted context.
- The agent does not retain standing access to sensitive records between requests.
- An authorization cannot silently carry forward into a later execution.

## Existing post-gallery sections

### Useful access, designed carefully

**Heading:** An agent needs access to be useful. That access has to be designed carefully.

**Body:** Useful agents may need access to email, customer records, internal documents, CRM, billing, or other business systems. The workflow and its access cannot be designed as separate problems.

**Panel label:** Questions to answer before launch

1. What can it see?
2. What can it change?
3. Which actions require approval?
4. Where are credentials kept?
5. How can the team review what happened or remove access?

**Panel answer:** Worktree designs the workflow, runtime, access, and human controls together, then documents the agreed boundaries for the team.

### The relationship

**Heading:** We learn the operation before we build the system.

**Body:** A Worktree engineer works with the people who run the process, chooses the technical approach, connects the systems, tests against real cases, and stays involved after launch.

1. **Learn with the operators:** Work with the people who run the process and understand how decisions, exceptions, and handoffs actually work.
2. **Choose the technical approach:** Select the agent, workflow, runtime, and supporting tools that fit the job instead of forcing one standard setup.
3. **Connect the selected systems:** Configure the agreed systems, job-specific access, and human approval points together.
4. **Test real cases:** Use representative work to check accuracy, completeness, routing, and the places where a person should stay involved.
5. **Launch with clear limits:** Put the workflow into operation with its role, access, approvals, and review process documented.
6. **Stay involved after launch:** Review the work, make focused changes, and manage the system as the operation and portfolio develop.

### The start

**Heading:** Start with one job that is worth fixing.

**Body:** Worktree begins with one concrete process, not a company-wide AI roadmap. The first deployment gives us something real to understand, test, operate, and measure.

**First deployment:** One concrete process

- Recurring work the team can describe
- Real systems, decisions, and owners
- A clear standard for useful work
- A deployment Worktree can keep operating

### Build from what works

**Heading:** One working agent gives us a place to build from.

**Body:** Later workflows do not start from zero. Worktree has learned more about the systems, policies, approvals, and teams around the work. Over time, we can manage a growing set of agents, workflows, and runtimes.

1. **First working agent:** Learn one job deeply enough to put a useful system into operation.
2. **Adjacent workflows:** Build from the context, access patterns, and working relationships already established.
3. **Managed portfolio:** Operate and improve a growing set over time, with each addition scoped deliberately.

### Relatable work

**Heading:** Start where context has to become action.

1. **After a sales meeting:** Update the CRM, prepare the follow-up, assign next steps, and route commercial decisions to the account owner.
2. **During customer onboarding:** Gather the handoff, open the project, request missing information, and keep the next owners clear.
3. **When a request comes in:** Read the request, collect the right context, prepare the response, and ask for approval when needed.
4. **Before an account review:** Bring together recent activity, open decisions, risks, and the next actions for the team.
5. **During a finance review:** Collect the supporting records, flag discrepancies, prepare the review packet, and route questions to the right person.

### Access and control

**Heading:** Know what the agent can see, change, and ask someone to approve.

**Body:** Worktree configures selected systems and job-specific access. Actions can remain draft-only or require approval where a person should make the decision. The team should be able to review the work and remove access when needed.

**Qualified note:** For qualified deployments, Worktree can review runtime environment, credential handling, data boundaries, approvals, and recovery requirements with the customer.

**Access plan — Defined with the workflow:**

- **Selected systems:** Only the business systems agreed for the job.
- **Job-specific access:** Access shaped around the work the agent is responsible for.
- **Controlled actions:** Draft-only or approval-gated actions where the business decision should remain with a person.
- **Reviewable work:** A record the team can use to review what happened and what changed.
- **Removable access:** A clear path for removing access when the workflow, role, or relationship changes.
